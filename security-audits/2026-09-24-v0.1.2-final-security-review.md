## Executive verdict

The findings carried forward by the sixth remediation follow-up are closed at the signed `v0.1.2` release. The final review found two additional boundary cases while verifying commit `2056678`: a source could change from a file to a directory before MOVE selected shared versus exclusive locking, and staged overwrites could consume a temporary inode without reserving it. Both were remediated in `407407f`, covered by deterministic regression tests, and verified with the complete suite and an isolated Docker deployment.

No open finding from this audit series blocks `v0.1.2`. This is a point-in-time assessment of the reviewed code and deployment model, not a guarantee that the software contains no undiscovered vulnerability. The known product gaps documented in `SECURITY.md` remain outside this release decision.

## Closure chronology

The later audit exchange closed in three steps:

1. `eb0f2ad` metered copied bytes and entries, retained journals after failed rollback, strengthened filesystem synchronization ordering, and verified committed transactions during recovery. The sixth follow-up nevertheless found a power-loss window between restoring originals and durably recording an aborted transaction, plus a cross-budget directory MOVE race with writes to descendants.
2. `2056678` durably recorded `rolling-back` intent and operation progress before undoing anything. Its rollback became idempotent across restart. It also introduced the shared `Drive` mutation path, per-budget readers-writer locks, out-of-tree staging, exact cross-budget folder accounting, and deterministic web/WebDAV race tests.
3. Final adversarial review of `2056678` found that MOVE chose exclusive locking from a pre-lock `lstat`. A concurrent request could replace the apparent file with a directory before the lock was acquired, causing the directory to move under shared locking. The review also found that an overwrite added no quota entry but still needed an unreserved temporary staging inode. `407407f` closed both boundaries and generalized peak-entry reservation to Drive, calendar/contact, import, synchronization-log, and property staging.

The package version was then changed to `0.1.2` in signed commit `a91446c`, and the signed annotated `v0.1.2` tag was created at that exact commit and pushed to the public repository.

## Confirmed closure

### Crash-safe rollback intention

Before rollback begins, the journal now writes and synchronizes a `rolling-back` record containing the progress of every operation. The same rollback routine is safe to repeat after a crash. Recovery distinguishes prepared, rolling-back, committed, and aborted transactions and converges each toward its intended state without interpreting an already-restored original as replacement content.

Regression tests inject crashes when rollback intent is recorded, during each of two undo steps, and after rollback completes but before the aborted marker. Each restart preserves the original content, removes the transaction record when recovery succeeds, and remains unchanged under a second recovery pass.

The prior deterministic reconstruction—where resurrection of the prepared record deleted the restored original—no longer succeeds against this protocol.

### Cross-budget directory MOVE serialization

The web application and WebDAV now use the same `Drive` mutation implementation. Ordinary changes take shared locks for their physical budget, while every MOVE takes all involved budget locks exclusively and in stable order. Choosing exclusivity no longer depends on a file type observed before locking.

The original descendant-upload race is closed for both interfaces: an upload already committed before measurement moves with the folder and is billed, while an upload that reaches commit after the exclusive MOVE begins waits and then fails cleanly because its parent moved. Cached usage for the user and Family budgets matches fresh recounts.

A further regression changes the source from a file to a directory immediately before MOVE acquires its locks, then attempts a child upload after measurement. The upload cannot enter the moving tree, the destination receives no unbilled child, and both budgets remain exact.

### Peak staging entries are reserved separately from quota entries

Storage reservations now distinguish:

- Persistent entries, which affect the owning user's or Family quota and file-count limit.
- Peak physical entries, which protect the filesystem's byte and inode reserves while temporary staging files exist.

An overwrite therefore adds zero persistent entries but reserves one physical staging entry before creating it. The same invariant covers Drive uploads, calendar/contact objects, multi-item imports, synchronization logs, and property files. Recursive copies continue to claim each staged entry before creation.

At a simulated filesystem state with exactly the configured inode reserve remaining, Drive and bookkeeping overwrites now return `507` before creating their temporary file and leave the original unchanged.

## Independent verification

Verification of the final release contents included:

- Complete automated suite: **102 tests passed, 0 failed, 0 skipped**.
- Focused regression coverage for the pre-lock file-to-directory MOVE race, concurrent descendant upload, peak Drive staging inode, peak bookkeeping staging inode, rollback crash boundaries, repeated recovery, cached-versus-recounted usage, and absence of leaked reservations.
- JavaScript syntax checks for all changed modules and tests.
- `docker compose config`, `git diff --check`, and Git object-integrity checks.
- An isolated Docker Compose build of MyCloud, the thumbnail worker, and the pinned Caddy service.
- HTTPS response through that Compose project's own Caddy endpoint, including HSTS and the expected security headers, plus direct upstream response from MyCloud.
- Inspection found no leftover journal records, staging files, or transaction artifacts after the smoke test.
- The uniquely named smoke-test containers, networks, and volumes were removed, and Colima was stopped afterward.

The final verification was run from macOS. The preceding remediation author separately reported the full suite passing on Linux and macOS and a successful Docker smoke test at `2056678`; this final review did not repeat the Linux run after `407407f`.

## Residual risk and future work

The audit series is closed for `v0.1.2`, but normal security maintenance remains necessary. In particular, retain the deployment and backup guidance and the known gaps in `SECURITY.md`, including stronger interactive-login authentication, file versioning, and password-protected public links. Continue dependency and base-image review, platform testing, restore drills, and private vulnerability intake.

Any later material change to authentication, authorization, sharing, filesystem layout, transaction recovery, proxy trust, media parsing, or storage admission should receive targeted regression coverage and a new security review rather than relying on this closure.
